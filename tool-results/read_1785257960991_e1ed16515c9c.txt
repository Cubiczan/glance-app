to &quot;Phase 1: Input&quot;\">​</a></h3><p>The user encrypts sensitive data off-chain and submits it to a smart contract using opaque <strong>handles</strong> (32-byte identifiers that reference the encrypted data stored in the Handle Gateway).</p><ol><li>The user sends a plaintext value to the <strong>Handle Gateway</strong> via the SDK</li><li>The Handle Gateway encrypts it with <a href=\"/protocol/kms#ecies-encryption-scheme\">ECIES</a> using the KMS public key and stores the ciphertext in an <strong>AWS S3 bucket</strong>.</li><li>The Handle Gateway returns a <strong>handle</strong> and an <strong>EIP-712 signed proof</strong> attesting the handle's validity.</li><li>The user calls a function on a smart contract that uses the <strong>NoxCompute</strong> library (e.g. <code>Nox.add(handleA, handleB)</code>)</li><li>NoxCompute validates handle proofs and type compatibility, computes a deterministic result handle, grants transient ACL access on it, and <strong>emits an event</strong> containing the input and output handles.</li></ol><p>At this point, the on-chain transaction is complete. The encrypted result does not exist yet: it will be computed off-chain.</p><h3 id=\"phase-2-compute\" tabindex=\"-1\">Phase 2: Compute <a class=\"header-anchor\" href=\"#phase-2-compute\" aria-label=\"Permalink to &quot;Phase 2: Compute&quot;\">​</a></h3><p>The off-chain pipeline picks up the event and executes the computation inside a secure environment.</p><ol><li>The <strong>Ingestor</strong> polls new blocks from the blockchain RPC, filters NoxCompute logs, groups events by transaction, and publishes a <code>TransactionMessage</code> to <strong>NATS JetStream</strong>.</li><li>The <strong>Runner</strong> pulls the next message from the queue.</li><li>The Runner requests the encrypted operands from the <strong>Handle Gateway</strong>, providing an ephemeral RSA public key.</li><li>The Handle Gateway retrieves the object from its <strong>AWS S3 bucket</strong> and coordinates with the <strong>KMS</strong> to perform <a href=\"/protocol/kms\">decryption delegation</a>: the KMS computes the ECDH shared secret and encrypts it with the Runner's RSA key.</li><li>The Runner decrypts the inputs locally (RSA decrypt the shared secret, HKDF key derivation, AES-GCM decrypt), executes the computation, and encrypts the result with ECIES using the KMS public key.</li><li>The Runner submits the encrypted result to the Handle Gateway and acknowledges the <code>TransactionMessage</code> received from <strong>NATS JetStream</strong>.</li></ol><h3 id=\"phase-3-output\" tabindex=\"-1\">Phase 3: Output <a class=\"header-anchor\" href=\"#phase-3-output\" aria-label=\"Permalink to &quot;Phase 3: Output&quot;\">​</a></h3><p>When the user wants to read a result, the protocol performs decryption delegation so that only the authorized user can recover the plaintext.</p><ol><li>The user generates an ephemeral RSA keypair and sends a decryption request to the Handle Gateway, authenticated with an EIP-712 signature.</li><li>The Handle Gateway verifies the signature and checks the <strong>on-chain ACL</strong> to confirm the user has viewer permission on the handle.</li><li>The Handle Gateway requests decryption delegation from the KMS: the KMS computes the shared secret and encrypts it with the user's RSA public key</li><li>The user receives the ciphertext, encrypted shared secret, and nonce, then decrypts locally: RSA decrypt the shared secret, derive the AES key via HKDF, and AES-GCM decrypt the ciphertext</li></ol><p>The KMS never sees plaintext data. Only the final recipient (user or Runner) performs the actual decryption.</p><h2 id=\"handles\" tabindex=\"-1\">Handles <a class=\"header-anchor\" href=\"#handles\" aria-label=\"Permalink to &quot;Handles&quot;\">​</a></h2><p>A <strong>handle</strong> is a 32-byte identifier that references an encrypted value stored in the Handle Gateway. It does not contain the ciphertext itself.</p><div class=\"language- vp-adaptive-theme\"><button title=\"Copy Code\" class=\"copy\"></button><span class=\"lang\"></span><pre class=\"shiki shiki-themes github-light github-dark vp-code\" style=\"--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e;\" tabindex=\"0\"><code><span class=\"line\"><span>[0]      [1------4]    [5]     [6]     [7---------------------31]</span></span>\n<span class=\"line\"><span>Version   Chain ID    Type   Attrs       prehandle (25 bytes)</span></span></code></pre></div><table tabindex=\"0\"><thead><tr><th>Segment</th><th>Size</th><th>Description</th></tr></thead><tbody><tr><td>Version</td><td>1 byte</td><td>Handle format version (currently <code>0x00</code>)</td></tr><tr><td>Chain ID</td><td>4 bytes</td><td>Chain ID encoded as uint32; binds the handle to a specific blockchain</td></tr><tr><td>Type</td><td>1 byte</td><td>Solidity type of the encrypted value (uint8, bool, address, etc.)</td></tr><tr><td>Attributes</td><td>1 byte</td><td>Handle attributes/properties (e.g. uniqueness)</td></tr><tr><td>Prehandle</td><td>25 bytes</td><td>Truncated keccak256 hash (deterministic for computation results, random for user inputs)</td></tr></tbody></table><p>For computation results, the prehandle is derived from the operator, input handles, contract address, caller, timestamp, and output index. <code>isViewer</code>) before serving decryption material to a user.</p><h2 id=\"encryption\" tabindex=\"-1\">Encryption <a class=\"header-anchor\" href=\"#encryption\" aria-label=\"Permalink to
